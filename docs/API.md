# Контракт интеграции v1

Базовый адрес задаёт администратор через ERP_BASE_URL, например https://HOST/BASE/hs/access/v1. ERP_USERNAME и ERP_PASSWORD — отдельные учётные данные сервиса, не пароль GitHub. Удалённый адрес требует HTTPS. Redirect запрещён, таймаут 5 секунд, ответ ограничен одним МиБ. Неверный JSON или версия не принимаются; повтор записи автоматически не выполняется.

Ответ: `{ "api_version": 1, "data": ... }`. GET /health возвращает data.system = 1c-enterprise. X-Portal-Actor содержит base64 UTF-8 имени вошедшего пользователя портала; браузер этот заголовок не задаёт. POST требует UUID Idempotency-Key.

1С должна аутентифицировать доверенный портал и самостоятельно сопоставлять его actor с действующей учётной записью и ролью. Поле роли из браузера не является полномочием. Публикация без защищённой аутентификации не считается готовой интеграцией.

Тест HTTP-клиента использует явно локальный имитатор и доказывает транспортный контракт, а не работоспособность HTTP-публикации 1С.

GET /actors/me возвращает data.actor и data.role (admin, requester, approver, guard). Отображаемая роль берётся из 1С, а не из параметров браузера или is_staff Django. В 1С профиль ищется по PortalUsers.Login; отключённые, удалённые и неоднозначные сопоставления отклоняются. Эта прикладная политика не заменяет настройку нативных прав 1С и аутентификации HTTP-публикации.

## Заявки

GET /references: data содержит массивы visitors, employees, checkpoints, purposes с UUID id и name, до 500 записей каждого вида. GET /requests: data.items, последние 100 доступных заявок, поля id, visitor, requester_login, status, starts_at, ends_at. Время содержит явный UTC-offset. Заявителю возвращаются только его записи; портал дополнительно отклоняет чужую строку целиком.

POST /requests: visitor_id, host_id, checkpoint_id, purpose_id, starts_at, ends_at; actor передаёт доверенный сервер портала отдельным заголовком. Автор/роль/статус из формы не принимаются. Подтверждение: data.id и status=submitted. Для повторов одинакового Idempotency-Key сервер обязан атомарно хранить автора, SHA payload и результат; тот же ключ с другими данными должен давать 409. ЭТО ТРЕБОВАНИЕ К ПРЕДСТОЯЩЕМУ HTTP-СЕРВИСУ 1С: серверное хранилище команд пока не реализовано.

Портал сохраняет UUID и payload до отправки, при потере ответа сохраняет их для точного повтора, после подтверждения меняет команду. Это клиентская часть протокола, сама по себе она не доказывает отсутствие дублей в 1С. Сквозная HTTP-публикация остаётся открытой.
