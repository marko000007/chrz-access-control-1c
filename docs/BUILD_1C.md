# Проверка сборки в чистой 1С-базе

Установленная платформа задаётся ONE_C_BINARY; по умолчанию используется локальная учебная 8.3.27.1606. Сами дистрибутив и пользовательские базы в Git не включены.

Для новой проверки выберите ещё не существующее имя базы внутри .local/1c:

```sh
python scripts/one_c.py create --base-name acceptance
python scripts/one_c.py load --base-name acceptance
python scripts/one_c.py check --base-name acceptance
python scripts/one_c.py smoke --base-name acceptance
```

Команда create не перезаписывает существующую базу. Имена ограничены буквами/цифрами ASCII, дефисом и подчёркиванием; выход за каталог проекта запрещён. Логи и JSON — .local/1c/logs/ИМЯ. Проверка создания требует файл результата с кодом 0 и наличие 1CD, smoke требует новый JSON ok=true; устаревший отчёт перед запуском удаляется. Проверяются thin/server контексты, затем реальные серверные сценарии с rollback.

22.11.2026 весь цикл прошёл в новой базе clean-20261122, созданной с нуля; источник — только XML/BSL из репозитория. Результат, SHA-256 каждого исходного файла и отметка о непроверенной локальной HTTP-связи — reports/1c-clean-build-v1.json. Это не сквозное испытание сети Python → 1С и не промышленная установка.

## Комплект по индивидуальному заданию №4

Конфигурация называется `ПодворныйВиталийОлегович70204645`. Готовая выгрузка с вымышленными связанными примерами — `one_c/releases/ПодворныйВиталийОлегович70204645.dt`. Создайте **новую** файловую базу в Конфигураторе 8.3.27.1606 и выберите «Администрирование → Загрузить информационную базу». Загрузка `.dt` заменяет содержимое целевой базы, поэтому рабочую базу не выбирайте.

В режиме Предприятия доступны четыре подсистемы. Отчёты имеют управляемые формы с периодом, формированием и табличным документом; его можно просмотреть и вывести средствами платформы с учётом ограничений учебной версии. Бизнес-процессы имеют карты маршрутов: согласование/выдача и разбор/решение. Прикладное имя входа оператора должно соответствовать Login в PortalUsers; примеры — `assignment.1.admin`, `assignment.1.guard`, `workflow.1.approver`. Эти имена относятся к вымышленным прикладным профилям; пароли/пользователи платформы в комплекте не создаются автоматически.

Воспроизводимая сборка в новой отдельной базе (команды явно открывают платформу):

```sh
python scripts/build_metadata.py
python scripts/one_c.py create --base-name assignment-clean --allow-gui
python scripts/one_c.py load --base-name assignment-clean --allow-gui
python scripts/one_c.py check --base-name assignment-clean --allow-gui
python scripts/one_c.py smoke --base-name assignment-clean --allow-gui
python scripts/one_c.py assignment --base-name assignment-clean --allow-gui
python scripts/one_c.py export --base-name assignment-clean --allow-gui
```

Подготовка новых примеров допускается только в пустой базе, повторная приёмка проверяет уже записанные результаты. Экспорт перезаписывает только выпускаемый `.dt` в `one_c/releases`; исходные пользовательские базы не изменяются.

Повтор браузерной проверки (Python с Django и Playwright, установленный Chrome):

```sh
python scripts/verify_assignment.py --base-name assignment-clean --allow-gui-1c
```

Пять отчётов в Python-интерфейсе доступны сотруднику проходной/администратору по `/reports/assignment/`. Они читают реальные таблицы 1С через выбранный локальный адаптер; для них нужна обновлённая конфигурация подключённой базы. Проверочная база не переключает действующую `.local/local-erp.json` автоматически. Старт окон по умолчанию остаётся отключён.
